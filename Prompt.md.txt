# PARAVALVES — MASTER PRODUCTION-GRADE ERP  CRM  ENGINEERING PLATFORM

## Complete Product, Architecture & Engineering Specification

You are the principal software architect, staff engineer, database architect, security engineer, DevOps engineer, QA engineer, UX architect and product engineer responsible for building a complete production-grade business management platform for Paravalves.

This is NOT a prototype.

This is NOT a demo-only application.

This is NOT a collection of disconnected CRUD screens.

Build a fully integrated, secure, scalable, auditable and production-ready ERP + CRM + Engineering + Inventory + Procurement + Project + Finance platform that can become Paravalves' primary internal business system.

The existing business uses Holded, Zoho, Excel, Google Drive and manual workflows. The new platform should consolidate the relevant capabilities into one system while adding Paravalves-specific automation.

# 90. THE CORE PRODUCT PHILOSOPHY

The system must not merely RECORD business activity.

It must UNDERSTAND business activity.

Bad

Stock = 13.

Good

15 required. 13 available. 2 incoming tomorrow. Order expected to be fulfilled tomorrow.

Bad

Lead created.

Good

New website lead received 18 minutes ago. Assigned to Sales. No contact yet. Follow-up due in 5 hours.

Bad

Project 72%.

Good

Project is 72% complete. Engineering and drawing are complete. Procurement is waiting for 2 components. Expected delay 1 day.

The system should turn raw business data into actionable operational intelligence.

# 92. FINAL INSTRUCTION TO THE ENGINEERING AGENT

Before writing significant amounts of code

1. Inspect the existing repository.
2. Identify the existing stack.
3. Identify existing infrastructure.
4. Identify existing database.
5. Identify existing authentication.
6. Identify existing integrations.
7. Produce an architecture plan.
8. Produce a databaseentity relationship plan.
9. Produce a module dependency graph.
10. Produce a phased implementation plan.

Do not destroy working existing functionality.

Do not rewrite infrastructure without reason.

Do not introduce dependencies unnecessarily.

Do not ask for confirmation for every small implementation decision.

Make reasonable engineering decisions and document them.

However, when a decision would materially alter business requirements, stop and identify the decision explicitly.

After each major phase

 Run tests.
 Run type checks.
 Run lint.
 Run build.
 Check migrations.
 Check security.
 Check database integrity.
 Check affected workflows.

Never mark a feature complete merely because it compiles.

At the end, perform a full system audit against this specification.

Generate a final

1. Feature completion report
2. Database integrity report
3. Security report
4. Performance report
5. Test report
6. Deployment report
7. Known limitations report

Any missing feature must be explicitly identified.

Do not claim 100% completion if something is incomplete.

The final system must be production-grade, secure, performant, maintainable, auditable and genuinely usable by Paravalves' employees.
